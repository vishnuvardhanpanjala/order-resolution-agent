## Judge validation

| | human: OK | human: not OK |
|---|---|---|
| judge: pass | 37 | 2 |
| judge: fail | 0 | 0 |

- Base rate (replies humans call not OK): 2/39 (5%)
- Catches bad replies (judge fails what humans call not OK): 0/2 (0%)
- Passes good replies (judge passes what humans call OK): 37/37 (100%)
- No agreement score on purpose. With few bad replies, a judge that passes everything would still "agree" most of the time.
- Only 2 bad replies labelled. The catch rate can't be trusted below 5.
- 39 labels is a small sample. Treat these rates as rough.
- Replies the judge blocked in this run (ours): T037. A blocked reply is swapped for a fixed "a person will reply" message, so a wrong block becomes a hand-off. The table above leaves blocked replies out (the customer never saw them), so read these by hand.

## What these numbers do not prove

- The tickets are synthetic and were written by the same person who wrote the policy. Real customers write things we did not think of.
- 63 tickets is small. One ticket is almost 2 points of accuracy.
- The expected outcomes come from our own policy table. If the table is wrong, a "correct" answer can still be bad for the customer.
- The mock systems never lag, never return half-written data, and fail only where we told them to.
- English and Singlish only.
- A live run on the same prompts can move a few points, because models are not fully repeatable.
- No real usage, so no adoption, cycle-time or reopen-rate numbers. See `07_rollout.md` for how those would be measured.
